# KB Viewer — Improvement Plan (for implementation)

Assessment of `site/` (static viewer: `index.html` + `app.js` + `styles.css`, data from
`kb-data.js`, generated by `tools/build-kb-site.js`). 99 notes today; grows over time.
Source of truth stays `knowledge_base/`; the viewer is read-only. No build step beyond
`node tools/build-kb-site.js` and no external runtime dependencies — keep it that way.

Verdict: good desktop skeleton, but (a) a content-rendering bug breaks grammar notes, (b) mobile
UX is broken, (c) the linked/graph nature of the KB is invisible. Work the phases in order;
each phase is independently shippable.

---

## Phase 1 — Correctness: fix the markdown renderer (highest impact)

The renderer in `app.js` (`markdownToHtml` / `inlineMarkdown`) is a partial reimplementation and
silently mangles real content. Verified: **64 ` ``` ` fenced code blocks** exist in the data and
are NOT handled — grammar formula diagrams and conjugation blocks render as broken paragraphs.

Do this:
1. **Fenced code blocks.** Detect lines matching `^```` (optionally with a language tag), buffer
   every line verbatim until the closing fence, and emit `<pre><code>…</code></pre>` with the
   inner text HTML-escaped and **no inline markdown applied** (ASCII diagrams must survive). This
   must run before paragraph/list/heading logic so fence interiors are never reinterpreted.
2. **Ordered lists** (`^\d+\.\s`) and **nested lists** (indentation-based) — several notes use them.
3. **Blockquotes** (`^>\s`), **italic** (`*x*` / `_x_`), **plain links** (`[text](url)` → `<a target="_blank" rel="noopener">`), and **headings 4–6**.
4. **Horizontal rule** (`^---$` / `***`) — but only outside frontmatter (frontmatter is already
   stripped in the build step, so body `---` is safe to treat as `<hr>`).
5. Add `.noteBody pre` styling: monospace, horizontal scroll, soft background, padding, rounded
   corners; ensure long ASCII diagrams scroll instead of overflowing the pane on mobile.

Acceptance: open `grammar-att-sats` and `grammar-v2-ordfoljd` — the `结构公式` diagrams render as
clean monospace blocks; no stray ``` ``` ``` or merged lines anywhere.

(Optional, lower risk: swap the hand-rolled renderer for a tiny vendored markdown lib only if you
can do it with zero network deps and keep the custom `[[wikilink]]` → button hook. Otherwise just
extend the existing functions — that's the lighter, safer path.)

## Phase 2 — Mobile UX (the broken experience)

Current `@media (max-width: 760px)` stacks panes as sidebar → **detail → results**, so tapping a
result at the bottom updates a detail pane above the fold with no feedback. Replace the stacked
layout with an explicit **two-view (list ⇄ detail) navigation model** on small screens:

1. On mobile, show **one view at a time**: the results list by default; opening a note slides in a
   full-screen detail view with a persistent **“← Back to list”** bar at the top. Back returns to
   the list at its previous scroll position.
2. Collapse the sidebar on mobile into a **sticky top bar**: search input always visible; filters
   and stats behind a “Filters / Stats” disclosure (`<details>` or a toggle) so content is reachable
   without scrolling past a wall of chrome.
3. On note open (mobile), set focus to the detail heading and scroll the detail pane to top.
4. Drop `selectFirstVisible()` auto-open on mobile (it targets an invisible pane). Keep it on desktop.
5. Replace the fragile `height: calc(100vh - 250px); min-height: 520px` magic numbers with a flex
   column that uses `min-height: 0` + `flex: 1` so panes fill available height at any size. Test the
   1120px (tablet) breakpoint too — it currently inherits the same awkward fixed heights.
6. Ensure tap targets ≥ 44px and that the search input doesn't trigger iOS zoom (font-size ≥ 16px).

Acceptance: on a 375px viewport, you land on the search + list, tap a note, read it full-screen,
and tap Back to return where you were — no manual scrolling to find content.

## Phase 3 — Make the link graph visible (core value of an Obsidian-style KB)

CLAUDE.md requires bidirectional `[[wikilinks]]`. The viewer only shows forward links inline. Add:

1. **Backlinks panel** in the detail view: “🔗 被引用 (Linked from)”. Precompute a reverse index
   either in the build step (add `backlinks: []` to each note in `build-kb-site.js`) or in `app.js`
   at load from the existing `links` arrays. List each source note as a clickable item with its type
   badge. Prefer computing it in the build step so the data is canonical.
2. **Forward-links summary** at the foot of the detail (“→ 链接到”), de-duplicated from the body,
   with **missing-target** links visibly flagged (reuse the existing `.missingLink` red styling) so
   broken links surface — this doubles as KB health feedback.
3. (Optional, nice-to-have) a small **local graph** view (the selected note + its 1-hop neighbors)
   using inline SVG, no library. Defer unless Phases 1–4 are done.

Acceptance: opening `arbeta` shows which sentences/topics link to it; clicking a backlink navigates.

---

## Phase 4 — Navigation, deep-linking, and search polish

1. **URL deep-linking + history.** Reflect the selected note in `location.hash`
   (`#note=<slug>`), read it on load, and `pushState` on navigation so the browser **Back button
   retraces wikilink trails** and notes are shareable/bookmarkable. This is the biggest
   desktop-navigation gap today (wikilink clicks currently replace the detail with no way back).
2. **Keyboard support:** `/` or `Ctrl/Cmd-K` focuses search; ↑/↓ move through results; Enter opens
   the highlighted result; Esc clears search / returns to list on mobile.
3. **Search-term highlighting** in result titles/excerpts and optionally in the opened note.
4. Show a **match snippet** (context around the first hit in the body) in result items, not just the
   leading excerpt, so full-text hits are explained.

---

## Phase 5 — Visual / metadata polish (lower priority)

1. Surface frontmatter as **badges**: `known: true` → “✅ 已掌握”, `cefr`/SFI level chip, `ordklass`
   chip. (Field is wired in the build step; 0 notes set `known` today but the badge should be ready.)
2. **Color-code type badges** (word/phrase/sentence/grammar/topic/source) consistently across result
   list, detail header, and backlinks for fast scanning.
3. **Dark mode**: `@media (prefers-color-scheme: dark)` palette via the existing CSS variables; the
   file already declares `color-scheme: light` only.
4. **CJK typography**: detail `<h2>` titles use Georgia, which renders Chinese poorly; titles often
   contain Chinese. Use a font stack that includes a CJK fallback for headings, matching `.noteBody`.
5. Remove the redundant truncated `excerpt` shown as `detailMeta` at the top of an opened note — it
   duplicates the body's opening lines.

## Constraints & notes for implementation

- **No new runtime dependencies; no network calls.** Must keep working from `file://` and on GitHub
  Pages. Vanilla JS/CSS only.
- `kb-data.js` is regenerated by `tools/build-kb-site.js`. If you add fields (e.g. `backlinks`), edit
  that script and document regeneration. Note: `node` is **not installed on this machine** — the
  GitHub Actions workflow `.github/workflows/kb-site.yml` regenerates and publishes on push, so don't
  hand-edit `kb-data.js`; change the generator and let CI rebuild (or note that the dev needs node).
- Don't break the existing `[[wikilink]]` → in-app navigation contract or the `escapeHtml` safety
  (all user/markdown content must stay escaped; only the renderer emits tags).
- Keep `index.html` data-driven; avoid hard-coding note types (use the existing `typeOrder`/`typeLabels`).
- Test matrix: desktop ~1440px, tablet ~1024px (the 1120px breakpoint), mobile 375px; plus a
  grammar note (code fences), a topic note (many links), and a long source note.

## Suggested sequencing

Phase 1 → 2 → 3 are the substance (correctness, mobile, link graph). 4 and 5 are polish. Ship each
phase as its own commit so regressions are easy to isolate.
